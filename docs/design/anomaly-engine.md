# アノマリー分析エンジン 設計

対象: Dukascopy の 1 分足からアノマリー候補を検証し、エントリーポイントを抽出・表示する機能。

実装状況: 段階 1〜6（§8）を実装済み。経済指標カレンダーは GMO クリック証券から取得（分析には使わない）、AI アシストは設定の接続テスト（OpenAI 互換 API の GET /models）に合格すると、設定した LLM で抽出 SQL を生成する。

## 1. 決定事項

| 論点 | 決定 |
|---|---|
| 市場データ | Dukascopy の BID / ASK 1 分足。チャート用 JSON API から取得 |
| 対象銘柄 | 固定にせず、**ユーザーが任意のペアを追加**できる。初期登録は USDJPY・XAUUSD と、AUDJPY・AUDUSD・CADJPY・CHFJPY・EURAUD・EURJPY・EURUSD・GBPAUD・GBPJPY・GBPUSD・NZDJPY（symbols.json がないときだけ。保存済みの一覧は変えない） |
| リアルタイム結果検証 | **行わない**。外部のリアルタイム API（GMO コインなど）は使わない。エントリーの結果は、取り込んだ履歴で確定させる（§6.4） |
| データ保存 | 1 分足は月別 Parquet、分析結果は DuckDB、設定・モード・銘柄は JSON（§4） |
| 保存場所 | `%LOCALAPPDATA%\AnomalyStudio\`。`data\` の場所だけ設定で変更可 |
| 実行の既定 | 手動実行。週次スケジュールは任意（設定でオン） |
| 経済指標 | GMO クリック証券の経済指標カレンダーを表示用に取得（分析・ポイント抽出には使わない） |
| エンジンの検証 | 合成データの単体テスト（§6.2） |

## 2. 計算仕様

| 項目 | 仕様 |
|---|---|
| 市場データ | Dukascopy BID / ASK 1 分足。UTC で取得し JST へ変換して解析 |
| 評価期間 | 30 / 90 / 180 / 365 日。365 日 = 基準日−365 日 〜 基準日−1 日。日跨ぎ Close 用に基準日当日も使う |
| 候補母集団 | 1440 Entry 時刻 × 保有 1〜60 分 × Long/Short = 172,800 候補（LogicVersion 2。1 までは保有 3〜30 分の 80,640 候補）。決済は Entry の足から保有分数後の足の始値（10 分なら 9:00 → 9:10） |
| 価格 | BID Open → BID Open。Long raw = Close − Entry、Short raw = Entry − Close。net = raw − 期間平均 spread（Entry・Close の両方がある取引の Entry 時点 Ask−Bid の平均） |
| 指標 | サンプル数 n、勝数、勝率（net > 0）、合計、1 取引平均、σ（raw の標本標準偏差 ddof=1）、利益効率σ = 合計 / (σ·√n)、平均 spread |
| スコア平均 | 30 / 90 / 365 日の平均（180 日は表示のみ） |
| 品質除外 | 30 / 90 / 365 日それぞれで、最大サンプル数の 80% 未満の候補をスコア正規化・ポイント抽出の母集団から外す（行は削除しない） |
| スコア | 勝率重視 = 勝率平均 / 母集団最大 × 100、利益効率 = 利益効率σ平均 / 最大 × 100、最大利益 = 平均変動の 30/90/365 平均 / 最大 × 100。時間効率（最大利益基礎値 / 保有時間）は、単位があり銘柄をまたいで比べられないため廃止した（列・既定モードとも削除） |
| ポイント | 保有 3〜15 分（勝率重視BO は 1・3・5・10・15・30・60 分で、短期 30・中期 90・長期 365 日の勝率がすべて 55% 以上の候補だけ）、TOP50、半開区間 [Entry, Close) で時間帯重複を除外（Close == 次 Entry は可）。tie-break: score 降順 → Entry 昇順 → 保有 昇順 → Long 先 |

銘柄ごとの差分は「銘柄プロファイル」で持ち、銘柄固有の候補や固定時刻の除外は持たない。

### 2.1 統計の補強（2 章の列の計算は変えない）

| 項目 | 仕様 |
|---|---|
| 勝率の信頼下限 | 期間ごとに、勝率の Wilson スコア区間（95%、z = 1.96）の下限 `win_rate_lcb_{30,90,180,365}` と、その 30 / 90 / 365 日平均 `win_rate_lcb_avg`。172,800 候補から勝率の点推定で上位を選ぶと、サンプルの少ない候補が偶然の高勝率で上位に来る（30 日期間は n ≈ 20〜30 で標準誤差が約 10 ポイント）。下限で並べると、同じ勝率でもサンプルの多い候補が上になる。正規化スコアや順位の列は持たない（0〜1 の値なので銘柄をまたいで比べられる）。この列で並べる既定モード「勝率（信頼下限）」は廃止した（`ModeDefinition.RetiredIds`。保存済みの modes.json から起動時に取り除く）が、列は自作モードの SQL で使えるように残す |
| 安定性の指標 | バックテスト系の画面で、確定した取引の損益列（Entry 時刻順）から平均損益の t 値（平均 ÷ 標準誤差。±2 が偶然でない目安）、平均の 95% 信頼区間（正規近似）、プロフィットファクター（総利益 ÷ 総損失）、最大ドローダウン（累積損益の最大の落ち込み）、最大連敗数を出す（`BacktestStatistics`）。値幅は表示単位 |
| ランダム基準 | 同じ画面で、確定した取引と同じ取引日・同じ件数・同じ取引時間帯・保有 3〜15 分の範囲（保有時間を限るモード = 勝率重視BO はその保有時間）でポイントを無作為に選んだ場合の合計損益を 200 試行計算し、平均と「実績が上回った試行の割合」を出す（`RandomBaseline`、乱数の種は固定）。複合ポイントでは銘柄も無作為に選ぶ。順位付けが無作為より良いかを常に確かめるための基準線で、最適化確認では選定に使ったデータでの上振れの大きさが、ウォークフォワードでは先の期間での実力が分かる |

### 銘柄プロファイル

`symbols.json` に 1 銘柄 1 レコードで持つ（`SymbolProfile`）。設定画面の「銘柄」グループで、同梱の Dukascopy 銘柄カタログ（主要 FX 63 ペア・貴金属 2 種、`SymbolCatalog`）から追加・有効化・削除する。

| 項目 | 意味 |
|---|---|
| `id` | 銘柄 ID（USDJPY）。保存フォルダ名と DB のキー |
| `dukascopyInstrument` | Dukascopy の銘柄コード（USD/JPY、XAU/USD） |
| `unitSize` / `unitLabel` | 表示単位。JPY クロスは 0.01 = 1 pips、その他の FX は 0.0001 = 1 pips、貴金属は USD 建て |
| `fallbackSpread` | 実測 spread が取れないときの控除値（価格単位、XAUUSD は 0.50） |
| `enabled` | 取込・分析・表示の対象か |

取込・分析・エントリー展開・結果確定はすべてこのレコードを参照する。コードに銘柄名の分岐は置かない。

## 3. アプリ内での位置づけ

| 画面 | 内容 |
|---|---|
| データ抽出設定 | 「分析」カード（銘柄ごとの取込状況・最新の分析、分析を実行 / データのみ更新 / 中止）と、モードの一覧。**モード = ポイント抽出の定義**で、勝率重視 / 勝率重視BO / 利益効率を既定として同梱（勝率（信頼下限）は廃止）。保存済みの modes.json に無い既定モードは起動時に無効の状態で追加する（既存の抽出結果を変えない）。既定モードの SQL が以前の版の既定の形のままなら、起動時に今の既定の SQL に置き換える（`ModeDefinition.Upgrade`。編集した SQL は変えない）。各行の「編集」でモード詳細を開き、名前・説明・SQL を編集する。画面や設定はモードを**名前**で覚えるので、名前は一意にする（`ModeDefinition.ValidateName`: 空・前後の空白・同じ名前・「すべて」・ファイル名に使えない文字は不可）。名前を変えるとエントリー画面の覚えている選択も書き換え、選択肢はモードが変わると作り直す。自作のモードは削除でき（確認あり。選んでいたエントリー画面は「すべて」に戻る）、既定モードは削除できない代わりに「既定に戻す」で既定の名前・説明・SQL に戻せる。既定モードの SQL を既定から変えると、既定の SQL の更新が当たらず、ウォークフォワードは DuckDB を通り、複合モードの並びは既定の指標のまま（詳細画面に注意を出す）。取込・分析の実行中は保存・削除しない |
| モード詳細 / AI アシスト | 抽出 SQL の編集。保存時に最新の分析結果で試行して、SQL の誤りをその場で表示する。AI アシストは要望から LLM（POST /chat/completions）で SQL を生成する。プロンプトは `ModeSqlPrompt`（表の定義・列の意味と単位・必須の規則・書き方の見本）。生成した SQL は文法チェック（`ValidateModeSqlAsync`: 行を読まずに実行し、文法・列名・必須の列を確認）し、通れば LLM に指示文と SQL が一致しているかを照合させる（`ModeSqlPrompt.ReviewSystem`、応答は {"match", "issues"} の JSON）。文法エラーや不一致なら「修正を依頼」で問題点と一緒に再送する（照合自体ができなかったときは止めず、テスト抽出で確かめる）。テスト抽出（最新の分析結果で実行）に成功した SQL だけ設定に反映できる |
| エントリー / ダッシュボード | 最新の分析結果から、有効な銘柄 × 有効なモードのポイントを展開（エントリー画面は選んだ 1 日、ダッシュボードの「次」は前後 24 時間）。結果は取り込んだ履歴で確定し、未取込の分は「未確定」 |
| ウォークフォワード・バックテスト | 取引日ごとに、評価サイクルで決まる時点の分析結果から選んだポイントで評価し、日 / 週 / 月ごとに集計（6.6）。「実行」で計算。合計行の上に安定性の指標とランダム基準（§2.1）を出す。取引明細（分析基準日付き）と集計（指標・ランダム基準を含む）を CSV に保存（ドキュメント\AnomalyStudio） |
| 最適化確認 | 最新の分析結果のポイントを指定期間の各日に当てはめ、日 / 週 / 月ごとに集計。分析期間と重なる期間は選定に使ったデータそのものでの成績。安定性の指標・ランダム基準・CSV 保存は同上 |
| 設定 | 銘柄、データの保存場所（表示とフォルダーを開く）、起動時の差分取込、週次の自動分析、分析結果の保持数 |
| 経済指標 | GMO クリック証券の経済指標カレンダーの画面が読む月別 JSON を取得して表示（`ClickSecCalendarSource`・`ClickSecCalendarParser`。取得したものは保存して再利用） |

## 4. データ基盤

### 4.1 構成

| 用途 | 保存先 | 理由 |
|---|---|---|
| 1 分足 | **Parquet**（`data\market\{銘柄}\{yyyy-MM}.parquet`、ZSTD 圧縮） | 変わらないデータ。DuckDB から直接クエリでき、ファイル単位でバックアップ・再構築できる |
| 候補統計・run | **DuckDB**（`data\anomaly.duckdb`） | 列指向で 172,800 行 × 数十列の集計・順位付けが速い。SQL でモードを定義できる。組み込みでサーバー不要（DuckDB.NET） |
| 設定・モード・銘柄 | **JSON**（`settings.json`、`modes.json`、`symbols.json`） | 値が少なく人が読める。書き込みは一時ファイル経由で置き換え、壊れた場合は `.broken` に退避して既定値で起動 |

- DuckDB のファイルは同時に 1 接続からしか安全に書けないため、読み書きは `AnalysisDatabase` に集約し、1 操作ずつ直列に実行する。
- Parquet の読み書きは `AnalysisDatabase` が内部に持つ `MarketDataStore`（メモリ上の DuckDB。別の接続・別の直列化）で行う。分析結果の保存や重い SQL の間も、画面の 1 分足の読込は待たされない。
- DuckDB は DELETE した領域を再利用はするがファイルを縮めない。古い run を消して空きが 64 MB 以上かつファイルの 25% 以上になったら、起動時と削除後にファイルを作り直して縮める（`COPY FROM DATABASE` で新しいファイルへ写し、順序番号を続きから振り直して入れ替える。失敗すれば元のまま）。
- 1 分足を Parquet に置くので、DuckDB ファイルを消しても再分析だけで復旧できる。
- 検討した代替: SQLite（行指向で分析が遅い）、TimescaleDB / ClickHouse（サーバー運用が必要）、LiteDB（分析クエリに弱い）。

### 4.2 テーブル

```text
-- Parquet（月別ファイル）
ts_utc, bid_open, bid_high, bid_low, bid_close, bid_volume, ask_open, ask_high, ask_low, ask_close, ask_volume

-- DuckDB
analysis_run     run_id, symbol, report_date, logic_version, created_at, duration_ms, bar_count, params(JSON)
backtest_points  symbol, report_date, cache_key, points, created_at（ウォークフォワード用に保存したポイント、6.6）
candidate_stats  run_id, symbol, direction, entry_min, hold_min, close_min, crosses_day,
                 n_/wins_/win_rate_/total_/mean_/sigma_/profit_eff_/spread_ × 30 / 90 / 180 / 365,
                 win_rate_avg, total_avg, sigma_avg, profit_eff_avg, spread_avg,
                 max_profit_base, quality_excluded,
                 score_win_rate, score_profit_eff, score_max_profit,
                 rank_win_rate, rank_profit_eff, rank_max_profit,
                 win_rate_lcb_30 / 90 / 180 / 365, win_rate_lcb_avg（§2.1。表の末尾。以前の版の DB には起動時に ADD COLUMN で足し、古い run は NULL）
```

値幅の列は価格単位（USDJPY は円、XAUUSD は USD）。値なしは NULL。1 run あたり 172,800 行（約 75 MB）で、銘柄ごとに設定した数（既定 3。画面は最新の run しか使わない）を超えた古い run は削除する。

設計当初に置いていた `entry_point` / `entry_result` / `ingest_log` は作らなかった。ポイントはモード SQL から、取引の結果は保存済みの 1 分足から毎回決定的に計算できるため、状態を二重に持たない。取込の進み具合は Parquet の最新・最古の時刻で判断する。例外として、ウォークフォワード・バックテストは基準日ごとの分析を保存せず、選んだポイントだけを `backtest_points` に保存して再利用する（1 分足から再計算できるので、消しても結果は変わらない）。

## 5. 処理の流れ

```text
Dukascopy ──(差分取込)──▶ Parquet ──▶ AnomalyEngine ──▶ candidate_stats ──▶ モード SQL ──▶ PointSelector（非重複 TOP50）
                           │                                                                        │
                           └────────────▶ TradeEvaluator（1 分足で結果を計算）◀────────────────────┘
                                                  │
                                                  ▼
                                   エントリー / ダッシュボード / バックテスト
```

## 6. 実装

### 6.1 Dukascopy 取込（`DukascopyMarketDataSource`、`MarketDataIngestor`）

- `https://freeserv.dukascopy.com/2.0/index.php?path=chart/json3` を使う。1 回で最大 30,000 本（約 1 か月）を返し、行は `[時刻(ms), open, high, low, close, volume]`。カーソルを進めながら取得する。
- ブラウザー以外の要求は 429 になるため、チャート画面と同じ User-Agent と Referer を付ける。429 と通信エラーは 5 秒間隔で最大 5 回まで再試行する。
- 当初案の bi5 データフィード（1 日 1 ファイル、LZMA）は、要求数が約 30 倍で制限にかかりやすく、価格の倍率も銘柄ごとに要るため採用しなかった。Dukascopy 公式の一括取得は S3（要 AWS アカウント・転送料は利用者負担）。
- BID と ASK を並行して取得し、同じ時刻の足だけを結合して保存する。形成中の足を保存しないよう、終端は現在時刻の 1 分前。保存済みの最新時刻の続きから取得する（差分取込）。初回は基準日−366 日から取得する。
- ウォークフォワード・バックテストで古い足が必要なときは、保存済みの最古の足より前の不足分だけを取得する（過去側の差分取込）。週末・年末年始で足がない分として、最古の足が 3 日遅れていても取得済みとみなす。
- 複数の銘柄は 2 銘柄ずつ並行して取り込む（`IngestAllAsync`。BID / ASK の並行と合わせて同時 4 要求まで。429 を避けるため増やさない）。通信や保存の失敗は銘柄ごとの結果（`IngestOutcome.Error`）にして他の銘柄を続け、画面のメッセージに失敗した銘柄を列挙する。利用者の中止だけは例外のまま伝える。
- 実測（2026-09-24）: USDJPY 1 年分 373,619 本を 39 秒、XAUUSD 356,071 本を 76 秒（1 銘柄ずつ）。

### 6.2 分析エンジン（`AnomalyEngine`、`PriceMatrix`、`AnalysisRunner`）

- 日（JST）× 1440 分の BID Open と Entry 時点 spread の行列を作り（欠損は NaN）、保有時間ごとに Close 側をずらした raw 値幅から、期間ごとの統計を計算する。
- 品質除外 → 正規化スコア → ランキング（同値は最小順位）を計算し、run として保存する。
- **速さの出し方**（計算の順序は変えない。足し合わせる順を含めて結果はビット単位で以前と同じ）
  - 行列は時刻 × 日の並び（`PriceMatrix`。同じ時刻の 365 日分が連続する）にする。エンジンは Entry 時刻と Close 時刻の列を先頭から読むだけになり、日 × 1440 分の並びより cache に乗る。
  - 並列は保有 28 本ではなく、保有 × Entry 時刻を 180 件ずつの塊（224 個）に分けて `Parallel.ForEach` で回す（20 コアでも偏らない）。
  - 順位付けは符号を反転した double の配列を `Array.Sort` で並べ（委譲の比較や LINQ を使わない）、3 つのスコアを並行して行う。既定モードの抽出（`PointSelector.BuiltInCandidates`）も構造体の鍵で並べ替える。
  - 連続して分析するとき（ウォークフォワード）は候補統計の入れ物（約 75 MB）を `reuse` で使い回し、長い期間の行列から `PriceMatrix.Window` で基準日ごとの窓を切り出す（配列を共有し、複製しない）。
- 実測（2026-09-25、Release、20 論理コア、USDJPY 実データ）: 80,640 候補 × 4 期間の計算は最小 27 ms（高速化前 70 ms）。うち正規化・順位付けが約 10 ms。候補を 172,800 に広げた後（2026-09-26）は最小 108 ms（うち正規化・順位付け 約 34 ms）、ウォークフォワードは 365 日換算で約 24 秒から約 43 秒。1 年分の Parquet 読込 約 120 ms、行列作成 約 15 ms、DuckDB への保存は別途 約 0.5 秒。`AnomalyStudio.Bench` で再計測できる。
- 段階ごとの所要時間は `Timing`（`AnomalyStudio.Core/Diagnostics/`）で計測し、アプリがログに書く（`計測 analysis/compute: 31 ms` の形。画面の読み直しは Debug レベル）。
- **正しさの確認**
  - 単体テスト（`AnomalyStudio.Core.Tests`）: 人工的な価格列（09:05 だけ +1 / +2 に跳ねる、spread 0.1 固定）で、勝率・合計・平均・σ（ddof=1）・利益効率σ・日跨ぎ・スコア平均・正規化・順位・品質除外（しきい値ちょうどを含む）・ポイントの tie-break と非重複判定を手計算の値と照合する。
  - 回帰テスト（`EngineRegressionTests`）: 高速化前のエンジンをそのまま残した参照実装（`ReferenceEngine`）と、乱数の価格（ランダムウォーク・欠損・休場）で全列をビット単位で照合する。窓の切り出し・入れ物の使い回し・配列の並べ替えも同じ結果になることを確かめる。計算仕様を変えるときは参照実装にも同じ変更を入れる。

### 6.3 モードとポイント（`ModeDefinition`、`ModeSql`、`PointService`、`PointSelector`）

- モードの SQL は `candidate_stats` に対する SELECT で、`direction` / `entry_min` / `hold_min` / `score` を優先順に返す。`$run_id` は最新の分析結果の番号に置き換わる。アプリはその順に時間帯の重ならない候補を最大 50 件選ぶ。
- 既定モードの SQL は抽出条件（品質除外なし・保有 3〜15 分。勝率重視BO は `hold_min IN (1, 3, 5, 10, 15, 30, 60) AND win_rate_30 >= 0.55 AND win_rate_90 >= 0.55 AND win_rate_365 >= 0.55`。勝率に値がない候補は除く）と並び順（score 降順 → Entry 昇順 → 保有 昇順 → Long 先）を表す。
- 安全策: SELECT / WITH で始まる 1 文だけを受け付け、変更系の命令と、ファイル・環境変数・ネットワークを読む DuckDB の関数（read_*、glob、getenv など。AI アシストの出力は未信頼データなので）を拒否する。実行はトランザクション内で行い、最後にロールバックする。
- 既定の SQL（`ModeDefinition.BuiltInSql` の形。勝率重視BO の保有時間の形を含み、`ParseBuiltIn` で判定）は、候補統計から直接同じ順で選べる（`PointSelector.SelectBuiltIn`、`BuiltInCandidates`）。ウォークフォワード・バックテストは、すべてのモードが既定の SQL なら DuckDB に 172,800 行を書かずにこの経路で選ぶ（結果が SQL と一致することを単体テストで確かめる）。

### 6.3.1 複合ポイント（`CompositePointSelector`、`ModeDefinition.CompositeMetric`）

- すべての有効な銘柄の候補を 1 つの順位表にまとめ、モードごとに最大 50 件のポイントを選ぶ。各ポイントは銘柄と、全銘柄を通した順位を持つ。
- 正規化スコアは銘柄ごとに最高値が 100 なので銘柄をまたいで比べられない。モードの SQL は候補の絞り込みとして使い、並びは銘柄をまたいで比べられる指標のもとの値（`CompositeMetric`）で決める。勝率重視・勝率重視BO = 平均勝率（`win_rate_avg`）、利益効率 = 利益効率σの平均（`profit_eff_avg`）。（廃止した勝率（信頼下限）は信頼下限の平均 `win_rate_lcb_avg` だった。以前の版の modes.json を読めるように指標の値は残す）（単位のある時間効率は廃止した）ユーザーが追加したモードは `compositeMetric` を持たなければ対象外。
- 並び: 指標の降順 → Entry 昇順 → 保有 昇順 → Long 先 → 銘柄 ID 順。銘柄をまたいでも時間帯が重ならない（同時に持つポジションは 1 つ）ように選ぶ。
- エントリー画面（「複合モード」。選んだ銘柄だけで作った複合ポイントを、最適化確認と同じくモードごとに取引時間帯とポイント数で絞り、取引日の曜日で絞る。条件は設定に保存したバックテスト・最適化確認と共通の値で、エントリー画面でも変えられる。銘柄別の表示も同じ時間帯・曜日で絞る）、ダッシュボード（「エントリー」を押して「複合」へ切り替え）、ウォークフォワード・バックテストと最適化確認（銘柄を複数選ぶと、選んだ銘柄だけで複合ポイントを作る）で使う。損益は各取引をその銘柄の表示単位（USDJPY は pips、XAUUSD は 1 USD = 1）に換算して合算し、pips と表記する（単位の違う銘柄を足しているので目安）。
- ウォークフォワード・バックテストでは基準日ごとに全銘柄を分析して選び、`backtest_points` に symbol = `*composite*` で保存する（キーは銘柄の組み合わせ・各銘柄の既定 spread・指標・モード SQL を含む）。データが足りない銘柄は候補から外し、その基準日のポイントは保存しない。銘柄のデータを削除すると複合ポイントの保存分も消す。
- 最適化確認では各銘柄の最新の分析から選び、分析基準日は最も新しいものを代表として使う。

### 6.4 エントリーの展開と結果（`TradeEvaluator`、`AnomalyWorkspace`）

- エントリー画面は、有効な銘柄 × 有効なモードのポイントを選んだ日（既定は今日）に展開する。銘柄別の「順位 上位N」は、銘柄 × モードごとに取引時間帯に収まるポイントを順位の高い順に N 件使う（バックテスト・最適化確認のポイント数と同じ `PointFilter.Select`。ウォークフォワード・バックテストの「エントリーに反映」で同じ条件を写せる）。上位 N 件は分析結果の全ポイントから選び、その日に市場が閉まっている時間（土曜の日中・月曜の開場前）のものは選んだ後で除く（繰り上げない）。過去・未来の日も最新の分析結果のポイントを当てはめる（その日に有効だった分析ではない）。ダッシュボードと画面上部の「次」は、昨日・今日・明日に展開して前後 24 時間に重なるものから選ぶ。
- 結果は保存済みの 1 分足で計算する。分析と同じ BID Open → BID Open で、控除する spread はその取引の Entry 時点の実測値。Close 時刻が取込済みの範囲より後なら「未確定」、Entry か Close の足がなければ「—」（休場など）。
- 起動時（設定でオン）に差分取込をバックグラウンドで行い、前日までの結果を確定させる。表示は 1 分ごとに読み直す。
- 1 分足は `QuoteCache` が銘柄ごとに読み込んだ範囲（最長 400 日）をメモリに持ち、毎分の読み直しは Parquet を読まずに切り出して評価する（`TradeEvaluator` は時刻順の足を二分探索で引き、辞書に写さない）。取込・削除で足が変わると（`AnalysisDatabase.MarketDataChanged`）その銘柄の分を捨てる。画面の読み直しが重なったときは新しい読み込みの結果だけを使う。
- 最適化確認は同じ計算を指定期間の各日に適用する。ポイントは最新の分析結果（直近 365 日）から選んでいるため、その期間と重なる結果は選定に使ったデータでの成績であることを画面に明記する。

### 6.5 実行タイミング（`AnalysisScheduler`）

- 既定は手動実行（データ抽出設定の「分析を実行」）。今日を基準日に、差分取込 → 分析を有効な銘柄ごとに行う。
- 週次スケジュール（設定でオン）: 毎分、直近の予定時刻（曜日 + 時刻、JST）より後の分析結果がない銘柄があれば実行する。

### 6.6 ウォークフォワード・バックテスト（`WalkForwardSchedule`、`WalkForwardBacktester`）

- 取引日 D に使う分析の基準日は評価サイクルで決まる。毎日 = D（前日までのデータ）、毎週 = D の週（月〜日）の直前の日曜（土曜までのデータ。週次スケジュールの既定と同じ）、毎月 = D の月の 1 日（前月末までのデータ）。集計の単位も同じサイクル。
- 基準日の分析は通常の分析と同じ計算だが、基準日の 0:00（JST）より後の価格を使わない。通常の分析は前日 23 時台 Entry の日跨ぎ Close に基準日当日の価格を使うため、そのままでは基準日の 0 時台の取引が先の価格を見た分析で選ばれうる。このため日跨ぎ候補は最終日の 1 件がサンプルから外れる。
- 分析対象の 365 日の先頭か末尾で足が 4 日を超えて欠けている基準日は分析せず、その基準日を使う取引日は取引なしとして画面に件数を出す。
- 実行時に、最初の基準日−365 日まで 1 分足が足りなければ先に過去側を取り込む。価格は 1 回だけ読み込んで検証期間全体の行列を作り、基準日ごとに窓（`PriceMatrix.Window`、基準日当日を使わない設定）をずらして分析する。候補統計の入れ物も使い回す（§6.2）。
- 実測（2026-09-25、Release、USDJPY、毎日サイクル）: 基準日 1 つあたり分析 約 40 ms + 3 モードの抽出 約 25 ms。30 日分 1.9 秒で、365 日換算 約 24 秒（高速化前 115 秒。ポイントの保存と取引の評価は別途）。
- 基準日の分析結果（172,800 行）は保存しない。すべてのモードが既定の SQL なら候補統計から直接選び（6.3）、ユーザーが編集した SQL を含むときはトランザクション内で一時的な run として追加し、モード SQL を実行してポイントを選んだあとロールバックする。選んだポイントは `backtest_points` に「銘柄・基準日・キー」で保存し、次回以降は分析をやり直さない。キーは計算方式の版・先読み防止の版・既定 spread・抽出件数・モード SQL のハッシュで、どれかが変われば計算し直す。新しく分析したときは、有効な他のモードのポイントもあわせて保存する。
- 結果は取引時間帯とポイント数で絞り込む（`PointFilter`、最適化確認も同じ）。基準日ごとに、Entry が開始時刻以降かつ Close が終了時刻以前（時間帯の境界や日付を跨がない）のポイントを、順位（モード SQL の並び。既定モードはスコア降順）の高い順に N 件使う。母集団は選び済みの最大 50 件なので、時間帯に収まるポイントが N 件に満たない基準日はその数だけになる。計算済みの取引に当てはめるだけで、ポイントの保存や再計算には影響しない。さらに取引日の曜日（月〜土）で絞る（順位の選び方には影響しない）。条件は設定に保存し、既定は 8〜19 時・上位 10・月〜土（月〜金だけを選べた旧版の設定で 5 日とも選んでいた場合は土曜を足す）。
- FX 市場の週の取引時間は NY 時間の日曜 17:00 〜 金曜 17:00（`Jst.IsFxMarketOpen`。JST では月曜 6:00〜土曜 6:00、米国の冬時間は 7:00）。土曜の JST の日付でも早朝は金曜 NY 時間の取引として数える。Entry か Close が市場の閉まっている時間（土曜の日中・日曜・月曜の開場前）にある取引は、足がなく取引できないので、集計・CSV・エントリー画面・ダッシュボードから除き、「データなし」の件数にも数えない。ランダム基準も、その日に市場が開いている範囲で無作為に選ぶ。

## 9. 残る課題とリスク

- Dukascopy のチャート用 API は公開の利用規約がない非公式の取得方法で、形式変更や制限の可能性がある。取得元は `IMarketDataSource` の背後にあり差し替えられる。
- ウォークフォワード・バックテストの毎日サイクルは、初回に検証日数分の分析を計算する（1 年分で分析・抽出 約 24 秒 + 保存と評価。2 回目以降は保存したポイントを使う）。`backtest_points` はモード SQL を変えるたびに増え、自動では削除しない（銘柄の削除時に消える）。
- 高速化は計算の順序を変えずに行った（ビット単位で同じ結果）。期間の入れ子を使った 1 パス化や SIMD は足し合わせる順が変わるので、行うなら計算方式の変更（`LogicVersion`）として扱う。
- 経済指標カレンダーは GMO クリック証券の画面用 JSON を読む非公式の取得方法で、形式変更や制限の可能性がある。AI アシストの SQL 生成は外部の LLM に依存し、生成結果は文法チェックとテスト抽出で確かめてから使う。API キーは接続テストに合格すると Windows の資格情報マネージャー（汎用資格情報 `AnomalyStudio:AiApiKey`、ログイン中のユーザーだけが読める）に保存し、設定画面や AI アシストを開いたときにそのキーで接続テストをやり直す（起動時には通信しない）。同じユーザーで動く別のプログラムからは読めるので、完全な保護ではない。
- Excel 形式のレポートは未対応。
- DuckDB のネイティブライブラリ（Windows x64）を配布物に含める必要がある。
- 統計面で未対応の論点: 解析は JST 固定なので、ロンドン・NY の夏時間で時間帯の癖が 1 時間ずれ、365 日窓の中で 2 つの体制が混ざる（銘柄プロファイルに基準市場を持ち市場時間で揃える案）。曜日や経済指標の発表前後を候補統計・バックテストから分けていない。損益はスリッページを見込まない（BID-BID − spread。ASK/BID 厳密方式への変更は未決）。複合ポイントの合算は銘柄の表示単位を足しているので目安。
